**Бизнес-модель:** B2C - Business-to-Consumer.

**Идея:** **IT QUEST** - IT-школа с веб/мобильной платформой, которая помогает учащимся 9-11 классов попробовать реальные задачи из разных IT-профессий до выбора ЕГЭ, вуза или платных курсов. Основной формат - очные профпробы на 90-120 минут, дистанционный формат доступен при невозможности прийти лично.

## Elevator Pitch

Учащиеся 9-11 классов часто хотят “пойти в IT”, но не понимают, какое направление им действительно подходит: тестирование, разработка, аналитика данных, UX/UI-дизайн или кибербезопасность. Из-за этого выбор ЕГЭ, вуза и курсов часто происходит почти вслепую - под влиянием трендов, рекламы, родителей или рассказов знакомых.

**IT QUEST** - это IT-школа коротких профпроб, где участники выполняют реальные мини-задачи из разных IT-профессий под руководством наставника. Основной формат проходит очно: подросток может почувствовать атмосферу занятия, задать вопросы и получить обратную связь. Если прийти лично невозможно, профпробу можно пройти дистанционно через платформу.

В отличие от обычных профориентационных тестов, IT QUEST показывает не абстрактные склонности, а реакцию пользователя на практические задачи. В результате старшеклассник осознаннее выбирает ЕГЭ, вуз или курс, а родители снижают риск потратить деньги на неподходящее обучение.

## 4. MVP и MLP

### MVP

MVP — минимальная версия продукта, которая позволяет проверить основной сценарий:

**участник выбирает профпробу, временно бронирует место, оплачивает участие, получает подтверждение, проходит занятие и получает результат.**

| № | История | Почему входит в MVP |
|---|---|---|
| 1 | Регистрация на платформе | Нужна для записи, оплаты и хранения результата. |
| 2 | Выбор IT-направления | Без выбора направления профпроба невозможна. |
| 4 | Просмотр формата профпробы | Участник должен понимать, как будет проходить занятие: очно или дистанционно. |
| 5 | Просмотр даты, времени, места или ссылки | Критично для очного и дистанционного формата. |
| 6 | Выбор свободного слота | Пользователь должен выбрать конкретное занятие. |
| 7 | Временная бронь места | Место удерживается на время оплаты. |
| 8 | Оплата профпробы | Нужна для проверки платной B2C-модели. |
| 9 | Подтверждение записи | Пользователь должен получить подтверждение участия. |
| 10 | Статус записи | Пользователь должен видеть, на каком этапе находится запись. |
| 12 | Прохождение практического задания | Главная ценность продукта. |
| 13 | Получение результата после профпробы | Завершает основной пользовательский путь. |
| 16 | Подтверждение оплаты и записи для родителя | Родитель должен понимать, что оплата прошла и ребёнок записан. |
| 18 | Внесение итога наставником | Позволяет участнику получить персональный результат. |
| 20 | Управление расписанием и местами | Без актуальных слотов и лимитов запись невозможна. |

### MLP

MLP — функции, которые делают продукт удобнее, понятнее и приятнее, но не являются обязательными для первой версии.

| № | История | Почему входит в MLP |
|---|---|---|
| 3 | Описание направления | Помогает лучше понять профессию до записи. |
| 11 | Напоминание о профпробе | Уменьшает риск неявки. |
| 14 | История пройденных профпроб | Позволяет возвращаться к результатам и сравнивать разные направления. |
| 15 | Понятная информация о профпробе для родителя | Повышает доверие к сервису. |
| 17 | Список подтверждённых участников для наставника | Помогает наставнику заранее подготовиться к занятию, но в MVP список можно передавать вручную. |
| 19 | Создание и редактирование профпроб | Нужно для масштабирования каталога, но первые профпробы можно добавить заранее. |

## История 1. Запись и оплата профпробы

**User Story:**  
Как учащийся или родитель, я хочу выбрать свободный слот, оплатить профпробу и получить подтверждение записи, чтобы гарантировать участие в очном или дистанционном занятии.

### Функциональные требования

| № | Требование |
|---|---|
| ФТ-1 | Пользователь может открыть каталог доступных профпроб. |
| ФТ-2 | Система показывает для каждой профпробы название, IT-направление, формат, дату, время, длительность, стоимость и количество свободных мест. |
| ФТ-3 | Пользователь может открыть карточку профпробы и посмотреть подробное описание занятия. |
| ФТ-4 | Пользователь может выбрать доступный слот и нажать кнопку “Записаться”. |
| ФТ-5 | Система проверяет наличие свободных мест перед началом записи. |
| ФТ-6 | Система временно бронирует место на ограниченное время, например на 15 минут. |
| ФТ-7 | Пользователь может перейти к оплате выбранной профпробы. |
| ФТ-8 | Система получает статус оплаты от платёжного сервиса. |
| ФТ-9 | После успешной оплаты система подтверждает запись и закрепляет место за пользователем. |
| ФТ-10 | Пользователь получает подтверждение записи с датой, временем, форматом, адресом или ссылкой для подключения. |
| ФТ-11 | Система сохраняет запись и её статус в личном профиле пользователя. |
| ФТ-12 | Если свободных мест нет, система не создаёт запись и предлагает выбрать другой слот. |
| ФТ-13 | Если оплата не прошла, система не подтверждает запись и показывает сообщение об ошибке. |
| ФТ-14 | Пользователь может отменить запись до начала профпробы по правилам сервиса. |

### Нефункциональные требования

| № | Требование |
|---|---|
| НФТ-1 | Для авторизованного пользователя с заполненным профилем процесс выбора слота и перехода к оплате должен занимать не более 3 минут. |
| НФТ-2 | Система не должна допускать записи сверх установленного лимита участников. |
| НФТ-3 | Информация о свободных местах должна быть актуальной на момент подтверждения записи. |
| НФТ-4 | Интерфейс записи и оплаты должен корректно работать на смартфонах и компьютерах. |
| НФТ-5 | Время загрузки карточки профпробы не должно превышать 2 секунд при нормальном интернет-соединении. |
| НФТ-6 | Данные пользователя и информация о записи должны храниться безопасно. |
| НФТ-7 | Система не должна хранить банковские данные пользователя внутри IT QUEST. |
| НФТ-8 | Адрес очного занятия и ссылка на дистанционное подключение должны отображаться понятно и без двусмысленности. |
| НФТ-9 | После успешной оплаты пользователь должен получить подтверждение записи без ручного обращения в поддержку. |

---

## История 2. Получение результата после профпробы

**User Story:**  
Как учащийся, я хочу получить результат после профпробы, чтобы понять, что мне понравилось, что было сложно и стоит ли дальше изучать это направление.

### Функциональные требования

| № | Требование |
|---|---|
| ФТ-1 | Наставник или администратор может открыть карточку подтверждённой записи участника. |
| ФТ-2 | Наставник может открыть форму внесения результата для конкретного участника. |
| ФТ-3 | Наставник заполняет результат профпробы: что получилось хорошо, что вызвало трудности и общий вывод по занятию. |
| ФТ-4 | Система проверяет, что обязательные поля результата заполнены. |
| ФТ-5 | Система сохраняет заполненный наставником результат. |
| ФТ-6 | Пользователь может открыть результат в личном профиле. |
| ФТ-7 | Результат содержит краткий вывод: что получилось хорошо, что вызвало трудности и стоит ли дальше изучать это направление. |
| ФТ-8 | Наставник может внести результат только для участника, который был записан на эту профпробу. |
| ФТ-9 | Система может отправить пользователю уведомление о готовности результата. |

### Нефункциональные требования

| № | Требование |
|---|---|
| НФТ-1 | Результат должен быть доступен пользователю не позднее чем через 24 часа после окончания занятия. |
| НФТ-2 | Формулировки результата должны быть понятны учащемуся и родителям без технического образования. |
| НФТ-3 | Результаты профпроб должны быть доступны только авторизованному пользователю, наставнику и администратору с соответствующими правами. |
| НФТ-4 | Экран результата должен корректно отображаться на мобильных устройствах и компьютерах. |
| НФТ-5 | Результаты профпроб должны сохраняться, чтобы пользователь мог вернуться к ним позже. |
| НФТ-6 | Текст результата не должен содержать категоричных формулировок вроде “тебе точно не подходит эта профессия”. |

**Глоссарий.**

| Термин | Описание |

**Описание.**

**Глоссарий.**

| Термин | Описание |
|---|---|

## 2. BDD — критический путь MVP

**Критический путь MVP:**  
Участник выбирает профпробу, бронирует место, оплачивает участие, получает подтверждение записи, проходит занятие и получает результат в личном профиле.

---

### Сценарий 1. Успешная запись на профпробу и получение результата

**Функция:** запись, оплата и получение результата профпробы.

**Дано:** учащийся авторизован на платформе.  
**И:** в каталоге есть профпроба “Тестирование”.  
**И:** на выбранный слот есть свободные места.  
**И:** стоимость профпробы составляет 990 рублей.

**Когда:** учащийся открывает карточку профпробы.  
**И:** выбирает доступный слот.  
**И:** нажимает кнопку “Записаться”.  
**И:** система временно бронирует место.  
**И:** пользователь оплачивает профпробу.  
**И:** платёжный сервис возвращает успешный статус оплаты.

**Тогда:** система подтверждает запись.  
**И:** место закрепляется за пользователем.  
**И:** пользователь видит подтверждение с датой, временем, форматом и адресом или ссылкой занятия.  
**И:** запись сохраняется в личном профиле.

**Когда:** учащийся проходит профпробу.  
**И:** наставник вносит результат по участнику.

**Тогда:** система сохраняет результат.  
**И:** учащийся может увидеть результат в личном профиле.

---

### Сценарий 2. Отказ при отсутствии свободных мест

**Функция:** запись на профпробу.

**Дано:** учащийся авторизован на платформе.  
**И:** в каталоге есть профпроба “Frontend-разработка”.  
**И:** на выбранный слот нет свободных мест.

**Когда:** пользователь открывает карточку профпробы.  
**И:** нажимает кнопку “Записаться”.

**Тогда:** система не создаёт запись.  
**И:** система показывает сообщение: “Свободных мест на эту профпробу нет”.  
**И:** система предлагает выбрать другой слот или другую профпробу.

## 4. API-First — JSON-контракты

API — это способ общения frontend и backend.

Например: пользователь нажимает кнопку **“Записаться”** на сайте.  
Frontend отправляет запрос на backend.  
Backend проверяет данные и возвращает ответ: запись создана или мест нет.

---

### Ручка 1. `POST /api/bookings` — запись на профпробу

**Описание:**  
Пользователь выбирает профпробу и слот. Система проверяет свободные места и создаёт запись.

**Запрос:**

```json
{
  "user_id": "user_1001",
  "trial_id": "trial_101",
  "slot_id": "slot_501"
}
```

**Ответ 201 — запись успешно создана:**

```json
{
  "booking_id": "booking_3001",
  "status": "confirmed",
  "trial_title": "Профпроба: Тестирование",
  "format": "offline",
  "date": "2026-05-20",
  "time": "15:00",
  "place": "Москва, образовательный центр IT QUEST, аудитория 204",
  "message": "Вы успешно записаны на профпробу."
}
```

**Ответ 400 — свободных мест нет:**

```json
{
  "error": "NO_FREE_PLACES",
  "message": "Свободных мест на эту профпробу нет. Выберите другой слот."
}
```

---

### Ручка 2. `POST /api/results` — сохранение результата профпробы

**Описание:**  
После занятия наставник заполняет результат профпробы. Система сохраняет результат в личном профиле учащегося.

**Запрос:**

```json
{
  "booking_id": "booking_3001",
  "student_id": "user_1001",
  "mentor_id": "user_2001",
  "strong_points": "Учащийся быстро понял логику поиска ошибок.",
  "difficulties": "Было сложно определить критичность ошибки.",
  "conclusion": "Направление тестирования стоит попробовать дальше."
}
```

**Ответ 201 — результат сохранён:**

```json
{
  "result_id": "result_8001",
  "status": "saved",
  "message": "Результат профпробы сохранён и доступен учащемуся в личном профиле."
}
```

**Ответ 403 — нет доступа:**

```json
{
  "error": "ACCESS_DENIED",
  "message": "Наставник может внести результат только для участника своей профпробы."
}
```

## 4. Стек технологий и обоснование

| Слой | Технология | Обоснование |
|---|---|---|
| **Frontend** | React | Используется для пользовательского интерфейса: каталога профпроб, карточки занятия, записи, оплаты, личного профиля, кабинета наставника и админ-панели. React выбран потому, что позволяет быстро собрать адаптивную веб-платформу для компьютеров и телефонов. |
| **Backend** | Node.js + Express.js | Отвечает за основную бизнес-логику: регистрацию, каталог профпроб, запись на занятие, оплату, результаты и разграничение доступа по ролям. Связка Node.js + Express.js выбрана как простое и популярное решение для быстрого создания API в MVP. |
| **Основная база данных** | PostgreSQL | Хранит пользователей, роли, профпробы, расписание, свободные места, записи, платежи и результаты. PostgreSQL подходит проекту, потому что в системе много связанных данных: пользователь связан с записью, запись — с профпробой, а результат — с конкретным участником. |
| **Кэш и временные данные** | Redis | Используется для временного удержания места на профпробе во время оплаты, кэширования популярных профпроб и очередей уведомлений. Redis выбран потому, что быстро работает с временными данными и снижает нагрузку на основную базу. |
| **Reverse proxy** | NGINX | Принимает внешние запросы, отдаёт frontend и перенаправляет API-запросы на backend. NGINX выбран как стандартная точка входа в веб-приложение: он помогает настроить HTTPS, маршрутизацию и отдачу статических файлов. |
| **Хранилище файлов** | S3-совместимое хранилище | Хранит материалы профпроб: задания, изображения, шаблоны интерфейсов, документы и вложения. Такое хранилище выбрано, потому что файлы удобнее хранить отдельно от PostgreSQL, не перегружая основную базу данных. |
| **Платежи** | ЮKassa API | Обрабатывает  оплату очных и дистанционных профпроб. ЮKassa API выбран, потому что подходит для российского B2C-проекта и позволяет не хранить банковские данные пользователей внутри IT QUEST. |
| **Email-уведомления** | Почтовый сервис | Отправляет подтверждение записи, уведомление об успешной оплате, напоминание о занятии и сообщение о готовности результата. Email выбран как простой и надёжный канал уведомлений для MVP. |
| **Push-уведомления** | Firebase Cloud Messaging | Отправляет быстрые напоминания о профпробе и уведомления о готовности результата. Firebase Cloud Messaging выбран, потому что push-уведомления помогают снизить риск неявки участника и быстрее донести важную информацию. |
| **Дистанционные занятия** | Яндекс Телемост | Используется для проведения дистанционных профпроб. Ссылка на онлайн-встречу хранится в системе и показывается участнику после успешной записи и оплаты. Готовый сервис выбран потому, что для MVP нет смысла создавать собственную видеоплатформу. |
| **Мониторинг** | Prometheus + Grafana | Отслеживают нагрузку, ошибки, доступность backend, состояние базы данных и другие метрики. Эти инструменты выбраны, чтобы команда могла быстро заметить проблемы с оплатой, записью или API после запуска MVP. |
| **Хостинг** | Yandex Cloud | Используется для размещения приложения, базы данных, Redis и файлового хранилища. Yandex Cloud выбран потому, что позволяет быстро развернуть MVP без покупки и настройки физических серверов. |

## 1. Hiring Plan — виртуальная команда под MVP

Для MVP нужна небольшая команда, которая сможет быстро проверить основной сценарий продукта:

**участник выбирает профпробу → бронирует место → оплачивает участие → получает подтверждение записи → проходит профпробу → получает результат.**

| Роль | Зоны ответственности |
|---|---|
| **Product Manager / Project Manager** | Формирует видение MVP, приоритизирует задачи, следит за сроками и согласует требования между командой, наставниками и администрацией IT-школы. В MVP эти функции может выполнять один человек. |
| **UX/UI Designer** | Проектирует пользовательский путь: каталог профпроб, карточку занятия, запись, оплату и экран результата. Делает интерфейс понятным для учащихся и родителей. |
| **Frontend Developer** | Разрабатывает веб-интерфейс для учащихся, родителей, наставников и администратора. Реализует каталог профпроб, запись, оплату, личный профиль и просмотр результата. |
| **Backend Developer** | Разрабатывает Backend API: регистрацию, роли, каталог профпроб, запись на слот, статусы оплат, результаты профпроб и права доступа. |
| **QA Engineer / Tester** | Проверяет основные сценарии: регистрация, запись на профпробу, оплата, отмена записи, внесение результата наставником и просмотр результата пользователем. |
| **Методист IT-профпроб** | Создаёт содержание профпроб: задания по тестированию, frontend-разработке, аналитике данных, UX/UI-дизайну и кибербезопасности. Следит, чтобы задания были понятны учащимся 9–11 классов. |
| **Наставник** | Проводит очные или дистанционные профпробы, объясняет задания, помогает участникам и заполняет результат после занятия. |
| **Администратор платформы / контент-менеджер** | Создаёт профпробы в системе, обновляет расписание, указывает стоимость занятий, следит за списками записавшихся и корректностью данных. |

## 2. Development Framework 

Для разработки MVP выбрана методология **Scrum с короткими итерациями по 1 неделе**.

### Почему Scrum подходит для IT QUEST

1. **Продукт требует быстрой проверки гипотез.**  
   Нужно быстро понять, удобно ли учащимся выбирать профпробы, готовы ли родители оплачивать занятия и достаточно ли полезен результат после прохождения.

2. **Требования могут меняться после первых тестов.**  
   После первых профпроб может выясниться, что нужно изменить карточку занятия, упростить запись, добавить больше информации для родителей или изменить формат результата.

3. **Команда небольшая, а задачи связаны между собой.**  
   Frontend, backend, методист и наставники должны работать синхронно: нельзя сделать запись без расписания, оплату без статуса записи, а результат без понятного шаблона обратной связи.

## 3. Командные ритуалы

| Ритуал | Зачем нужен | Когда и сколько |

# Практическое задание №6. Управление рисками

Выявить 4-6 ключевых рисков для  проекта. Указать их тип: внутренний или внешний. Оценить уровень рисков. Продумать стратегию реагирования

---

## Управление рисками

В соответствии с принципами управления рисками, цель данного этапа — заранее выявить угрозы, которые могут повлиять на запуск MVP, качество профпроб, доверие пользователей и финансовую устойчивость проекта.

Риски разделены на:

- **внутренние** — возникают внутри проекта и зависят от команды, продукта, процессов или технической реализации;
- **внешние** — связаны с рынком, пользователями, родителями, конкурентами или внешними сервисами.

Ниже представлены 6 ключевых рисков проекта IT QUEST и стратегии реагирования на них.

---

## 1. Риск: Низкий спрос на платные профпробы

Учащиеся и родители могут не понять ценность разовой платной профпробы. Родители могут считать, что бесплатных вебинаров, дней открытых дверей или роликов на YouTube достаточно для выбора IT-направления.

**Тип:** внешний, рыночный риск.

**Уровень риска:**  
Вероятность — средняя.  
Влияние — высокое.

**Стратегия реагирования:** смягчить.

**Действия:**

- запустить первые профпробы по сниженной цене;
- показать родителям конкретную пользу: учащийся не просто слушает лекцию, а выполняет реальную мини-задачу;
- добавить примеры результатов после профпробы;
- собрать отзывы первых участников и использовать их в продвижении;
- протестировать разные цены на очные и дистанционные профпробы.

---

## 2. Риск: Профпробы окажутся слишком простыми или скучными

Если задания будут слишком лёгкими, абстрактными или похожими на обычный урок, учащийся не почувствует реальный опыт IT-профессии. В таком случае продукт потеряет главное отличие от профориентационных тестов и бесплатных вводных занятий.

**Тип:** внутренний, продуктовый риск.

**Уровень риска:**  
Вероятность — средняя.  
Влияние — высокое.

**Стратегия реагирования:** предотвратить / смягчить.

**Действия:**

- привлекать методиста и практикующих IT-специалистов к созданию заданий;
- тестировать каждую профпробу на небольшой группе учащихся до полноценного запуска;
- после занятия собирать обратную связь: что было понятно, что было сложно, что понравилось;
- регулярно обновлять задания, чтобы они не выглядели устаревшими.

---

## 3. Риск: Проблемы с оплатой и подтверждением записи

Основной сценарий MVP зависит от записи и оплаты. Если пользователь оплатит профпробу, но запись не подтвердится, или наоборот место будет забронировано без успешной оплаты, это приведёт к потере доверия и ручным разбирательствам.

**Тип:** внутренний, технический риск.

**Уровень риска:**  
Вероятность — средняя.  
Влияние — высокое.

**Стратегия реагирования:** предотвратить.

**Действия:**

- использовать внешний платёжный провайдер;
- хранить статусы записи и оплаты отдельно;
- подтверждать запись только после успешной оплаты;
- логировать все операции оплаты и записи;
- дать администратору возможность вручную проверить спорную ситуацию.

---

## 4. Риск: Неявка участников на очные или дистанционные профпробы

Даже после записи участник может забыть о занятии, перепутать время, не найти аудиторию или не подключиться онлайн. Это снижает эффективность занятия и может приводить к пустым местам в группе.

**Тип:** внешний, поведенческий риск.

**Уровень риска:**  
Вероятность — высокая.  
Влияние — среднее.

**Стратегия реагирования:** смягчить.

**Действия:**

- отправлять напоминания за день и за час до профпробы;
- в подтверждении записи явно показывать дату, время, формат, адрес или ссылку на подключение;
- добавить возможность отмены или переноса записи заранее;
- для очного формата указывать, как найти аудиторию;
- для дистанционного формата заранее показывать ссылку на подключение;
- анализировать процент неявок по направлениям и времени проведения.

---

## 5. Риск: Нехватка наставников для проведения профпроб

Для масштабирования проекта нужны наставники, которые могут не только знать IT-направление, но и понятно объяснять задачи учащимся 9–11 классов. Если наставников будет мало, расписание будет ограниченным, а качество занятий может снизиться.

**Тип:** внутренний, операционный риск.

**Уровень риска:**  
Вероятность — средняя.  
Влияние — среднее.

**Стратегия реагирования:** смягчить.

**Действия:**

- подготовить шаблоны занятий для наставников;
- сделать единый шаблон результата профпробы;
- провести инструктаж наставников перед запуском;
- собирать обратную связь от участников по каждому наставнику;
- постепенно расширять команду только после подтверждения спроса.

---

## 6. Риск: Результат профпробы будет непонятен учащемуся и родителю

После профпробы пользователь ожидает понятный итог. Если наставник напишет слишком технический, короткий или категоричный комментарий, учащийся и родитель могут неправильно понять результат. Например, воспринять его как окончательный вердикт о профессии.

**Тип:** внутренний, продуктовый риск.

**Уровень риска:**  
Вероятность — средняя.  
Влияние — среднее.

**Стратегия реагирования:** предотвратить / смягчить.

**Действия:**

- использовать единый шаблон результата;
- разделить результат на блоки: что получилось хорошо, что вызвало трудности, общий вывод;
- избегать категоричных формулировок вроде “это точно твоё” или “тебе не подходит”;
- писать результат простым языком без сложных технических терминов;
- дать наставникам примеры хороших комментариев;
- проверять первые результаты вручную администратором или методистом.

## Итог

Самые критичные риски для IT QUEST связаны с тремя зонами:

1. **ценность продукта** — будут ли учащиеся и родители понимать, зачем платить за профпробу;
2. **качество занятия** — действительно ли профпроба даёт опыт, похожий на реальную IT-задачу;
3. **надёжность основного сценария** — запись, оплата и результат должны работать без сбоев.

На этапе MVP важно не запускать сразу много направлений. Лучше начать с небольшого набора профпроб, проверить спрос, собрать обратную связь и только потом расширять каталог.
